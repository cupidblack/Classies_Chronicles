# 1. Purpose and core invariants

This document remains necessary because it defines durable continuity semantics that a daily runbook cannot safely infer on every call. It does not replace the master and does not itself authorize canon or storage.

Core invariants:

1. exactly one accepted projection for an approved episode revision;
2. drafts, proposals and accepted events remain distinct;
3. corrections append or supersede with evidence rather than erase history;
4. public, internal and restricted data remain isolated;
5. B6 is a rights-filtered portable projection, not a substitute for source records;
6. a repository or database row is not proven to exist by a logical record definition.

# 2. Partitioning and custody

| Classification | Permitted content | Default custody |
|---|---|---|
| `PUBLIC` | Human-accepted A, exact approved public question, authorized public attribution | Approved public destination after explicit release authorization |
| `INTERNAL` | B1–B8, drafts, accepted/proposed event data, project and role records | Permission-filtered editorial/archive workspace |
| `RESTRICTED` | Challenge answer key, private diaries, identity documents, credentials and sensitive rights decisions | Purpose-specific approved custody; never ordinary B or public metadata |

A restricted field is never made public by embedding it in a model prompt, ZIP, alt text, image prompt, file name or ordinary handover.

# 3. Common logical envelope

Each instantiated record should contain, when applicable:

- `record_id`, `family`, `schema_id`, `schema_version`;
- `episode_id`, `day_id`, `legacy_id_refs`;
- `record_revision`, `parent_revision`, `base_revision`;
- `artifact_uri`, `storage_proof`, `captured_at`, `updated_at`, `actor`;
- `classification`, `sensitive_field_policy`, `audience`, `permitted_uses`;
- `source_refs`, `source_revisions`, `snapshot_ref`, `evidence_status`;
- `editorial_status`, `approval_evidence`, `effective_at`;
- `body`, `field_statuses`, `conflict_refs`;
- `integrity_digest`, `supersedes`, `superseded_by`, `dependent_asset_refs`.

Every missing value needs a typed status and reason such as `not_retrieved`, `not_verified`, `source_down`, `restricted`, `not_authorized`, `conflicting`, `editorial_hold`, `not_applicable` or `not_committed`.

# 5. Temporal, location and source snapshots

An `episode_context_snapshot` must preserve P/H/F as distinct data, not merely as a single "today" timestamp.

For each clock record:

- source URL or captured payload ID;
- original offset-aware value where returned;
- retrieval UTC;
- parsed local civil date/time;
- freshness;
- physical location;
- parse status;
- authority status.

An absent historical location, probe destination or team position is not inferred from the timestamp. Preserve `UNKNOWN_WITH_REASON` rather than guessing.

# 6. Append-only continuity events

Every `continuity_event_log` entry should include:

- immutable event ID;
- source A revision and cited scene/beat;
- fictional effective time and place;
- actor, mission and storyline identities;
- accepted pre-state;
- proposed delta;
- actual editorial status;
- approval evidence;
- predecessor/supersession/correction refs;
- dependent character, mission and storyline records.

Fictional events do not prove real-world activity. A real Koware task requires independent organizational evidence.

# 7. Accepted-state projection

Calculate the accepted projection with this order:

1. select the authorized episode and last accepted event head;
2. check accepted parent episode carry-forward and effective canon;
3. read accepted events in approved revision/sequence order;
4. exclude proposed, rejected, revoked or superseded events;
5. apply accepted deltas to scoped character, mission and storyline projections;
6. recompute only from accepted evidence;
7. preserve an exact source-event reference and base revision;
8. create no canon promotion from draft acceptance.

A causal invariant cannot be violated silently. A person remains stranded until an accepted return or relocation event changes that state. A character does not know a revelation found only in an unaccepted draft.

# 9. Mandatory fifteen-part B6

1. identity and revisions;
2. source and authority basis;
3. production calendar;
4. P/H/F temporal geometry;
5. cast and role spotlight;
6. character internal state;
7. mission and Edubeam state;
8. real Koware project boundary;
9. story event and scene dependencies;
10. Eternal Dreamfall V1–V6 derivation;
11. research and safety;
12. audience challenge state;
13. visual/media continuity;
14. QA, conflicts and revisions;
15. next-day handoff.

B6 must distinguish accepted state from proposed draft state and must omit challenge solutions and unauthorized personal data.

# 10. Challenge custody

Only `challenge_public_register` belongs in ordinary internal B. A public question may appear with exact approved wording and source revision.

`challenge_answer_key` may exist only under a separate secure commissioning/authorization and with a real restricted-custody owner. It must not be sent in ordinary A/B, copied into B6, placed in a comic prompt or accidentally rendered in media metadata.

# 11. Dependency and stale state

The production dependency chain is:

`approved calendar/canon/rights -> accepted story revision -> challenge revision -> comic/media plan -> assets -> release QA -> publication`

Changing A, canon, rights, challenge wording or mission state invalidates relevant downstream work until it is rechecked. Asset status must remain one of `NOT_COMMISSIONED`, `PLANNED`, `PROMPTS_CREATED`, `ASSETS_RENDERED_VERIFIED`, `ASSEMBLED_VERIFIED`, `QA_PASSED`, `APPROVED` or `STALE_SOURCE`.

# 12. Editorial decisions and conflicts

An editorial decision record must identify:

- proposal or decision scope;
- affected revision and assets;
- evidence;
- rationale;
- approver;
- effective timestamp;
- reversibility and rollback impact.

Conflicts are `ADVISORY`, `MATERIAL` or `BLOCKING`. A conflict must name the sources or observations, responsible owner, remediation and resolution state. An unresolved conflict is not converted into a default fact.

# 13. Safe writes and migrations

An ordinary daily instruction is not an archive write authorization.

Before an expressly authorized write:

1. verify owner-approved destination and ACL;
2. read the latest head and `base_revision`;
3. construct the exact diff;
4. recheck rights and challenge custody;
5. detect changed intervening revisions;
6. set `CONFLICT_REQUIRES_RECONCILIATION` and stop if a conflict exists;
7. execute an approved atomic or change-controlled operation;
8. read back the exact revision, hash and permissions;
9. mark `COMMITTED_VERIFIED` only after readback.

For schema migration, inventory old records, preserve legacy IDs and old B3/B7 meanings, map fields reversibly and test null/status semantics. Redaction or lawful erasure may require tombstones or downstream invalidation; it must not silently erase the audit trail or expose restricted history.

# 14. Episode compilation

Episode compilation requires a separate commission and the actual accepted revisions for all ten ordinary working days, or an owner-approved exception for missing components. It must not fabricate missing accepted days or auto-approve a title.

A new compilation must preserve component revisions, corrections, open arcs and challenge obligations. A separate media/comic operation requires a separately locked source revision and no answer leakage.

# 15. Required regression fixtures

Execute these only with clearly labeled fixtures or real authorized cases:

- Monday, Friday, second Monday, second Friday and episode 2 day 11;
- midweek chapter start and full-block rejection;
- P/H/F payload failures and distinct locations;
- wrong role index 1–10 instead of 1–40;
- proposed versus accepted event;
- supersession with event-history preservation;
- concurrent stale base revision;
- challenge solution in B6 or comic metadata;
- rights revocation invalidating a derivative;
- old `calendar_probe_record` migration;
- missing/deleted/changed record after a write.

A fixture run proves only fixture behavior. It does not prove live permissions or owner adoption.
